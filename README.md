## Supabase setup

- Enable email/password signup and email confirmation. Configure and verify production SMTP; this source does not presume working mail delivery.
- Set Site URL to the deployment origin. Explicitly allow `http://localhost:3000/register?confirmed=1`, `http://localhost:3000/register?auth=callback`, `http://localhost:3000/login`, and `http://localhost:3000/reset-password`. Add the same exact paths on the Vercel/deployment origin. Do not allow arbitrary production origins.
- Password-recovery requests call `resetPasswordForEmail` with same-origin `/reset-password`. Keep the Supabase recovery email template's confirmation link so the SDK receives the actual recovery callback. Do not replace it with a plain reset-page URL or a fake query flag.
- Google is opt-in: configure OAuth credentials in Supabase and its callback URL in Google Cloud, then set `NEXT_PUBLIC_ENABLE_GOOGLE_AUTH=true`. Registration returns to `/register?auth=callback`; login returns to `/login`.
- Yandex is deliberately disabled with an explanation, not mapped to Google or fake auth.
- Google registration preferences are temporarily held in session storage and applied to user metadata after callback. They contain only store name and requested plan, never credentials or tokens.
- Browser auth uses only the public anon key and original singleton `lib/supabase.js`. The lazy privileged singleton is deliberately isolated in `lib/supabaseAdmin.js`, guarded by Next's bundled `server-only`; this is a security-motivated departure from putting `supabaseAdmin` in the browser-imported module. No additional package is needed. All app database queries are server-side.
- Every API request verifies the Supabase access token with `auth.getUser`; owner IDs are never accepted from request bodies. Every privileged store lookup filters both `id` and `user_id`, then requires `marketplace='kaspi'`. Order reads/writes are scoped to that owned store. Service-role bypasses RLS, so those checks are mandatory, not replaced by RLS. Configure RLS on users/stores/orders/stock to deny anonymous access and prevent cross-owner reads/writes, especially direct browser writes to encrypted tokens or import metadata. Do not treat client-controlled `requested_plan` as entitlement.

## Persistence and recovery

- Login's checked-by-default remember-me control is functional. Checked: SDK sessions use localStorage and survive future browser visits until signout/expiry. Unchecked: SDK sessions use sessionStorage, survive same-tab reload/OAuth return, and normally end when that tab closes. Browser session restoration or duplicated tabs can retain/copy sessionStorage; this is not a server-enforced session lifetime. LocalStorage sessions may be shared across same-origin tabs.
- The adapter preserves Supabase's original `sb-<project>-auth-token` key. New SDK writes remove the other storage's stale copy. A non-secret sessionStorage preference selects the destination across OAuth redirects. Registration explicitly keeps its original persistent-session behavior.
- Blocked storage/quota errors fall back to this browser instance's memory without throwing during SSR/module loading. Login warns when the initial persistence probe fails; in that case reload loses the session and OAuth may need browser storage enabled. No implementation can delete data from browser storage while the browser denies access.
- A reset form is enabled only after successful SDK `initialize()` AND an observed `PASSWORD_RECOVERY` event with a valid session/user/deadline. An early singleton listener retains the real event before form mounting/hash cleanup. No auth method is awaited inside that listener. An arbitrary previous session, `INITIAL_SESSION`, `SIGNED_IN`, or query flag is insufficient.
- Recovery authorization is instance-memory only, expires with the original recovery session deadline, and is revoked on signout, changed user, ordinary reauthentication, or successful password save. Refreshing a reset page after the SDK has consumed the link requires a new email link. Initialization errors remain invalid even if another event arrives.
- Reset calls `updateUser({ password })`, validates exact confirmation, blocks concurrent submits, and ignores UI updates after unmount. Successful save leaves the SDK session active; `/login` exposes signout and a real `/dashboard` link. Registration has a real dashboard CTA; onboarding only enables its dashboard CTA after completed import.
- Recovery success text is generic to avoid disclosing account existence. Network/rate-limit/server errors use sanitized messages. No auth tokens or passwords are shown or stored in custom metadata.
- `/onboarding` has a browser session gate and redirects signed-out users to `/login`; recovery sessions go to `/reset-password`. Its static HTML contains no private data. The APIs independently authorize every request server-side, including resumed imports. Browser remember-me and recovery gates are unchanged.

## Token and cursor security

Generate a private 32-byte encryption key locally (example command, not a supplied secret):

```sh
node --input-type=module -e "import { randomBytes } from 'node:crypto'; process.stdout.write(randomBytes(32).toString('base64'))"
```

Set `KASPI_TOKEN_ENCRYPTION_KEY` to that base64 value only on the server. Token encryption uses AES-256-GCM, a fresh 12-byte IV, authenticated tag and a `v1` envelope. Rotating the key makes old stored tokens and cursors unreadable; reconnect each store after a planned rotation. Do not lose this key or put it in a browser bundle, source handoff, logs, screenshots, or chat.

The raw Kaspi token stays in a masked in-memory input until POST verification, is cleared on successful verification/logout, and disappears on unmount. It is never placed in storage, metadata, env, logs, or responses. An empty result is valid verification; there is no invented seller-identity endpoint. The supplied store name is a user label. No store is created until the actual Kaspi read succeeds. Verification returns only public store ID/name/connected state. Existing-store updates require ownership.

HMAC-SHA256 signed opaque cursors are workflow integrity tokens, not custom authentication/JWTs. They bind verified user, owned store, run ID, fixed dates, state, page, processed-page count, 24-hour expiry, and a REQUIRED server-derived SHA-256 fingerprint of the exact current `stores.api_token_encrypted` UTF-8 envelope string (not the raw token, with no trimming/re-encoding). The same private key is used with a dedicated HMAC domain prefix. Tamper, wrong owner/store and expiry fail. Cursors and public store labels may be saved in per-user sessionStorage; they cannot authenticate without a valid Supabase access token. Browser storage blocked: continuation is memory-only. No raw or encrypted Kaspi credential is stored there; only the signed workflow cursor contains its non-secret envelope digest.

Reconnecting a store creates a fresh encrypted envelope, even if the raw token is identical, and invalidates every previous cursor for that store. Legacy cursors without a valid fingerprint cannot bypass the check. Each resume compares against the currently owned store BEFORE any Kaspi page fetch or finished-cursor summary. The server re-reads the owned store after the upstream fetch before persistence, and again after summary before returning completion, to catch an intervening reconnect. A mismatch returns safe HTTP 409 with `code: KASPI_RESTART_REQUIRED`; no page advance or completed summary is returned. The client clears the old cursor, progress, summary and per-user saved resume, stays at the import step, and offers an explicit new import starting at NEW/page 0 against the current server connection. It does not fake verification, expose credentials or silently continue the old run. These checks are not a database transaction/lock: avoid concurrent reconnect/import/metadata edits; schema-level locking remains outside scope.

## Kaspi contract and limits

All upstream reads use native fetch on the server, the constant `https://kaspi.kz/shop/api/v2/orders`, raw `X-Auth-Token`, JSON:API content type, no-store, no redirects, bounded timeouts, and at most three attempts with capped retry delay. No user-provided relationship URL is fetched (SSRF boundary). Verification is ONLY page 0, size 100 (official allowed maximum), state NEW; it never traverses remaining pages. A valid token with 1001 NEW orders is accepted using a 100-order first page with pageCount=11/totalCount=1001. Verification still requires safe-integer consistent metadata, valid attributes, the exact expected bounded page length, bounded included entries and <=2 MiB response, but does not apply the product's full-import page/count caps. Large valid metadata cannot falsely label a credential invalid; supported-import limits fail separately during import with a safe incomplete-import error. Imports use page 0 onward, size 100, all six states NEW, SIGN_REQUIRED, PICKUP, DELIVERY, KASPI_DELIVERY, ARCHIVE, and fixed Unix-millisecond lower/upper date bounds exactly 14 days apart. No timezone offset is manually added.

The first sync request returns a signed initial cursor before fetching a page, making first-page retry stable. Each later POST processes at most one upstream page and advances only after validated response and persistence. Final signed state triggers a bounded DB summary, separately retryable. Pending/error/pause/retry states are real; progress shows processed pages and completed states, not a fabricated percentage. Pause finishes the current page. Work only runs while the tab's request loop is open; closing it does not schedule background jobs. A lost response can replay the prior cursor. New import freezes a new window; expired continuation must start again.

Malformed collections, missing/inconsistent camelCase meta.pageCount/totalCount, missing pages, too-large response (>2 MiB), >1000 pages per state, or a summary >10,000 unique orders fail incomplete rather than silently truncate. Kaspi calls time out at 7 seconds; DB calls at 8 seconds; summary scans have a 20-second admission deadline. API routes declare a 60-second Vercel maximum; confirm the deployed plan supports it. Permission/auth errors differ from 429/5xx/network failure. SDK/upstream bodies and secrets are never returned or logged.

Official date filters can select by state-assignment date. We fetch all states over one frozen window, then qualify actual attributes.creationDate, deduplicate by stable order code per owned store and resource ID within a page. State transitions and changing pagination mean this is not an atomic/exhaustive snapshot. Missing included entries are explicitly marked incomplete; we do not issue an unbounded request per order. `include[orders]=entries` is linked by relationship IDs, never positions. Product observations use masterproduct IDs from actual entries, not seller SKU or a full catalog. Optional quantity is ordered quantity, not stock. Unknown statuses are preserved. totalPrice is tenge, not minor units. All-order amount is not profit/revenue; completed-order amount is labelled separately.

**Actual stock read is unavailable through a verified public Kaspi API.** No invented inventory endpoint exists in this implementation. Order import never changes stock, base_stock, sold_since_base, availability or prices. Manual stock, settings and CSV/XLSX exports work with existing local tables; Telegram, Ozon/WB, EN translation, price rules, waybills, Email/Google Sheets/PDF report delivery remain unavailable. Future navigation items are disabled, not links to missing pages.

## Reporting semantics and safety

- All reporting GETs read existing `orders.data.kaspi`, never Kaspi network endpoints. Reports do not need `KASPI_TOKEN_ENCRYPTION_KEY`; imports still do. The browser calls server APIs using the SDK access token in an Authorization bearer header only. APIs verify `getUser`, then owner/store/marketplace, then scoped orders. Store discovery returns only ID/name/marketplace. No encrypted token is selected by reporting.
- Strict query parameters: `storeId`, `start`, `end` (YYYY-MM-DD, real calendar dates, 1–31 days). Orders additionally accepts `q` (100 characters), lowercase `status` bucket, `city` (200), positive `page`, `pageSize` (1–100), `format=json|csv`. Duplicate and unknown parameters fail. Default client period is 14 Almaty calendar days including today. Source timestamps are epoch milliseconds; date display and hour/day aggregation use IANA Asia/Almaty, including its historical offset changes.
- To avoid guessing DB JSON query/cast types before schema verification, the server reads the owned store in deterministic ID order in 1000-row pages, then validates/sanitizes/filters by actual creation date and sorts newest creation date plus local ID. The bounded scan cap is 10,000 stored rows per store, not only matching-period rows. More rows fail explicitly with 409 and no partial statistics/export. Reads have a 20-second admission deadline and existing DB 8-second timeout. Invalid dates are excluded with explicit availability warnings. Imported unique `(store_id,order_code)` remains required. Offset reads are not an atomic DB snapshot: pause imports during reports/CSV if strict consistency is required; concurrent inserts/deletes can shift pages. No snapshot/transaction/schema implementation is claimed.
- Completed-order sum is only `COMPLETED` order totalPrice in tenge, not settled revenue. Missing/malformed amounts stay null, valid zero stays zero. - `COMPLETED`, `CANCELLED`, `RETURNED` are distinct; cancelling/return-requested stay pending. Unrecognized statuses have their own bucket. Unknown cities remain in the all-order denominator. Activity is recent imported orders by creation date, not invented events. Day/hour counts are observed imported orders only.
